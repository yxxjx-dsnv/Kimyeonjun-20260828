# 올박스 — 팀 구매 + 확률형 뽑기

🔗 **배포:** https://albox-alwayz.vercel.app

오리파의 문제는 확률이 낮은 것이 아닙니다. **통이 안 보이는 것입니다.**
통이 안 보이면 확률은 검증할 수 없는 주장일 뿐입니다.

올박스는 1,000구좌를 전부 화면에 그리고, 뽑힐 때마다 통에서 빼고, 안 나온 것은 팀 안에서 바꿉니다.

## 오리파와 무엇이 다른가

| | 오리파 | 올박스 |
|---|---|---|
| **확률 고지** | 판매자 주장. 검증 불가 | **재고 ÷ 구좌.** 통을 세면 확인된다 |
| **구성품 검증** | 불가 | 1,000구좌 전체가 이름·시세·이미지와 함께 화면에 |
| **뽑힌 뒤 갱신** | 안 됨. 몰래 채워넣기 가능 | **비복원.** 빠진 만큼 확률이 갱신되고 화면에 보인다 |
| **안 나왔을 때** | 쓸모없는 카드 더미 | **팀 안에서 교환.** 아무도 교환 전보다 나빠지지 않는다 |

직접 조사한 근거가 첫 줄에 있습니다 — 다나와에서 수집한 오리파 **37건 중 확률을 적어 둔 것은 0건**,
"확정·보장"이라고 적은 것은 **30건(81.1%)** 입니다. 확률 대신 보장을 팝니다.

## 1. 어떤 문제를 풀었나 — 과제 1과의 연결

**컬처 시그널은 포켓몬 카드 열풍입니다.** 2026년은 포켓몬스터 출시 30주년이고,
크림 TCG 거래액이 2026년 1~4월 전년 동기 대비 +5,625%(4월 단월 +15,325%),
용산 아이파크몰 카드숍에 발매일 개점 전 600여 명이 줄을 섰습니다.

그 안에서 고른 문제는 **오리파**입니다. 가게가 내용물을 직접 구성해 무작위로 파는 상품인데,
확률 고지·구성품 검증·환불 기준 어느 것도 제도화돼 있지 않습니다. 그래서 확률을 공개해도
검증할 수 없고, 뽑혀도 갱신되지 않고, 몰래 채워넣어도 아무도 모릅니다.
대만에서는 카드사 폐업으로 3,000명 이상이 약 88~132억 원의 피해를 봤고, 같은 관행이
한국에도 퍼져 있다는 경고가 나와 있습니다.

**타깃은 30~40대 부모입니다.** 돈을 내는 사람이면서 문화 바깥에 있습니다. 카드숍은
아이들과 전문 리셀러의 공간이고, 시세도 은어(SAR·PSA·오리파)도 모른 채 들어가면
무엇을 샀는지조차 알기 어렵습니다.

**해결은 통을 보여주는 것입니다.** 확률을 잘 설명하는 것이 아니라, 확률이 계산되는
분모와 분자를 그대로 화면에 두는 것입니다. 1,000구좌를 전부 그리면 확률은 설명 대상이
아니라 세어보는 대상이 됩니다.

### 올웨이즈 기존 기능과의 차별점

올웨이즈에는 이미 **0원딜**(고가 제품 무료 증정), **다인딜**(인원이 모이면 파격가),
**올또**(현금 1억, 꽝 있음)가 있습니다. "공동구매 + 무료 당첨"은 신규성이 없습니다.

**올박스의 신규성은 형식이 아니라 그 위에 얹는 층에 있습니다** — 구성 전체 공개와 교환입니다.
그래서 형식은 올웨이즈의 기존 문법(팀 구매·0원딜)을 그대로 빌려 세 가지를 두되,
**확률 규칙은 하나로 통일했습니다: 확률 = 재고 ÷ 참여.**

| 형식 | 참여가 늘면 | 왜 |
|---|---|---|
| ① 팀 뽑기 | 확률이 **오른다** | 한 박스를 함께 뽑는다 — 재고는 그대로, 참여만 는다 |
| ② 브랜드 공동구매 | 환불 인원이 **는다** | 참여자 마진이 쌓여 전액 환불 재원이 된다 |
| ③ 0원 응모 | 확률이 **내린다** | 특가 수는 고정이고 응모만 는다 |

**①과 ③이 같은 규칙에서 정반대로 움직입니다.** 이것이 팀 효과가 마케팅 문구가 아니라
구조라는 증거입니다 — 박스를 나눠 쓰면 오르고, 나눠 가지면 내려갑니다.
③은 ①의 주장을 검증하는 대비군으로 같은 목록에 세워 뒀습니다.

## 2. 강조하고 싶은 부분 — 주요 설계 의도

### (1) 확률을 사람이 적지 않습니다 — 재고 나누기 구좌입니다

`P(g) = K_g / N`. 이것은 수식이 아니라 정의입니다. 근거가 필요 없습니다.
그리고 이것이 오리파와의 차이 전부입니다 — 오리파는 `K_g`를 공개하지 않으므로
`P(g)`를 계산할 수도 검증할 수도 없습니다.

코드에 사람이 확률을 조절할 수 있는 손잡이가 하나도 없습니다. 그것을 주석이 아니라
**검사로** 지킵니다 — `api/` 전체에 예산·곡선 파라미터가 선언돼 있으면 self-check가 깨집니다.

### (2) 팀 효과가 초기하분포에서 나옵니다 — 회사가 정한 숫자가 하나도 없습니다

```
                    C(N − K_g, n)
P_team(g, n) = 1 − ───────────────        K_g = 1이면 정확히 n / N
                      C(N, n)
```

재고가 1장이면 팀 인원 n에 대해 **정확히 n배**입니다. 저희가 아무것도 보태지 않습니다.
재고가 4장인 A등급은 9.87배이고, **반올림해서 10배라고 쓰지 않습니다.** 화면에 그대로 표시합니다.

v1은 이 "10배"를 예산으로 만들려고 했습니다. 대량 매입 원가 절감과 신규 고객 획득비
회수에서 배수를 뽑아 확률에 곱했습니다. 그 결과 1,000구좌 × 0.280% = 기대 배출 2.8개인데
재고는 1개인 모순이 남았습니다. v2는 배수 자체를 만들지 않습니다.

### (3) 비복원 추출이 천장을 대체합니다 — 도박사의 오류를 사실로 만듭니다

"많이 안 나왔으니 이제 나올 때가 됐다"는 생각은 복원 추출에서는 착각입니다.
오리파는 심지어 꽝카드를 다시 채워넣기까지 합니다.

비복원이면 참입니다. `P(g) = K_g / (N − j)`. 990구좌가 빠지면 S등급이 10%가 됩니다.
천장이라는 인위적 장치가 필요 없습니다 — 통이 줄어드는 것 자체가 천장이고,
그 사실이 화면의 숫자로 계속 증명됩니다.

### (4) 교환이 팀 확률을 개인 확률로 전환합니다 — 교환 없이는 팀이 아무 의미가 없습니다

**팀에 S가 나오는 것과 내가 S를 갖는 것은 다릅니다.** 교환이 없으면 팀이 아무리 커져도
개인 확률은 `K_g / N` 그대로입니다. 팀 효과는 존재하지만 나에게 도달하지 않습니다.

교환은 **Gale의 Top Trading Cycles**입니다. Shapley & Scarf(1974) JME 1(1) 6절 p.30에서
기술되며 David Gale에게 귀속됩니다. *"Shapley-Scarf의 알고리즘"이 아닙니다.*

| 성질 | 내용 | 출처 |
|---|---|---|
| 코어 배정 존재 | 결과가 코어에 속함 | Shapley & Scarf (1974) |
| 비공허성·유일성·파레토 효율 | 더 나은 배정이 없음 | Roth & Postlewaite (1977) |
| **개별 합리성** | **아무도 교환 전보다 나빠지지 않음** | Roth & Postlewaite (1977) |
| **전략 방지** | **거짓 신고해도 이득이 없음** | Roth (1982) |

이 성질들을 정리로만 두지 않고 검사로 옮겼습니다. 무작위 선호 프로파일 10,000건에서
나빠진 사람 0명, n≤6 전수 400회(최대 720배정)와 n=7~10 표본 60,000배정에서 지배 0건,
거짓 신고 3,000건에서 이득 0건입니다.

## 3. 설계 근거로 참고한 것

전부 [`docs/references.md`](docs/references.md)에 출처·시점과 함께 있습니다.
핵심만 옮기면 —

- **D2** 불확실성은 구매의도에 부정적이고 **자율성은 긍정적**입니다 → **지목** 기능의 근거
- **D4** 도박사의 오류가 비합리적 소비를 매개하고 **지각된 희소성이 조절**합니다
  → **비복원 공개**의 근거이자 **희소성 압박 UI 금지선**
- **D6** 루트박스 지출 ↔ 문제도박 r=0.26 (Trim and Fill 0.37), 15개 연구 → **꽝 없음**의 근거
- **D10** 자연빈도가 확률 오인을 줄입니다 → 확률 옆에 **항상 자연빈도 병기**
- **C2** 공정위 테무 제재 사유가 확률이 아니라 **조건 은닉**이었습니다
  → 팀 효과 고지를 첫 화면에, 초대자 개별 보상 없음
- **E4** 블라인드박스 문화에는 이미 교환이 있습니다 → 교환은 발명이 아니라 **이미 존재하는 행동**
- **E7** 올웨이즈는 이미 0원딜·다인딜을 운영합니다 → 형식을 새로 발명하지 않고 **기존 문법을 빌리되**, 신규성은 그 위의 구성 공개·교환 층에 둡니다

### 인용의 한계 — 우리에게 불리한 것도 적습니다

1. **D1과 D2가 상충합니다.** D1(Zhang & Zhang 2022)은 불확실성이 구매의도를 높인다고 하고
   D2는 낮춘다고 합니다. **우리가 채택한 D2는 제품 전제에 불리한 결과입니다.**
   채택 이유는 D2가 실행 가능한 설계 지침(자율성을 넣어라)을 주기 때문입니다.
2. **중국 표본의 한국 적용은 가정입니다.** D1·D4 모두 중국 소비자 표본입니다.
3. **D6의 r=0.26은 횡단 자료이고 원저자도 인과를 주장하지 않습니다.** 상관을 인과로 쓰지 않았습니다.
4. **TTC 전략 방지는 표본 검사이지 전수 증명이 아닙니다.** 가능한 거짓 신고 전체를 훑지
   않았으므로 반례가 없다는 것이 증명은 아닙니다.
5. **B5·B6은 커뮤니티/위키 출처입니다.** "커뮤니티에서 반복 지적되는 문제"로 명시하고,
   제도 공백 주장 자체는 언론 보도(B1)로 지탱합니다.
6. **타깃이 30~40대 부모라는 것은 가정입니다.** 근거(A6)는 20~40대 구매층까지만
   뒷받침합니다. 설문이나 인터뷰로 검증하지 않았습니다.

## 4. 겪은 어려움과 해결

### ① 확률 모델이 예산 기반이라 틀렸다는 것을 뒤늦게 발견했습니다 (v1)

**문제**: v1의 확률 엔진에 `CR_MIN`·`CR_MAX`·`N0`·`K`·`CAC`·`CAC_CAP`·`VIRAL_MAX`·
로지스틱 곡선이 있었습니다. 팀이 커질수록 확률이 오르는 이유가 "대량 매입으로 원가가
줄고 신규 고객 획득비를 회수하니 그만큼 확률을 올려준다"였습니다.

**원인**: 확률을 **회사가 정하는 값**으로 설계했기 때문입니다. 그러면 "확률이 정직하다"는
주장이 "우리 말을 믿어달라"와 같아집니다. 오리파와 구조가 같습니다.

**해결**: 재고 기반으로 바꿨습니다. 확률 = 재고 ÷ 구좌.

> **배운 것**: 정직한 확률은 잘 설명된 확률이 아니라 **분모와 분자를 보여주는 확률**입니다.

### ② 재고 기반으로 바꾼 뒤에도 모순이 남아 있었습니다 (v1)

**문제**: 재고를 분자로 두고도 거기에 팀 배수를 **곱하고** 있었습니다.
1,000구좌 × 0.280% = 기대 배출 2.8개인데 재고는 1개였습니다.

**원인**: "재고가 상한이다"와 "배수를 곱한다"가 양립할 수 없다는 것을 못 봤습니다.
self-check 5,631건이 전부 통과하고 있었습니다.

**해결**: v2에서 배수 자체를 없앴습니다. 초기하분포가 이미 팀 효과를 줍니다.
`P_team = 1 − C(N−K, n)/C(N, n)`이고, K=1이면 그 값이 **정확히 n/N**입니다.
회사가 만들려고 했던 그 10배가, 아무것도 보태지 않아도 수학에서 그냥 나옵니다.

> **배운 것**: 검사가 많은 것과 옳은 것을 재는 것은 다릅니다.
> **5,631건이 전부 통과하는 동안에도 모델은 현실과 다른 것을 재고 있었습니다.**
> 그리고 이 세 단계 — 예산 기반 → 재고 기반 + 배수 → 배수 제거 — 가 이 프로젝트의 핵심 서사입니다.

### ③ 오리파 확률 실측이 처음에 "100% 미공시"라는 거짓 수치를 냈습니다

**문제**: 오리파 91건의 상세 페이지를 받아 "확률 단어 0건 → 91/91 미공시"라고 판정했습니다.
확률이라는 **단어조차** 하나도 없다는 게 이상했습니다.

**원인**: 91건 중 84건이 다나와 **중개 링크**였고, 전부
`"현재 로딩중입니다. 해당 쇼핑몰로 이동 중입니다"`라는 578자짜리 브리지 페이지를
HTTP 200으로 돌려주고 있었습니다. 목적지는 JS로만 넘어갑니다.
**상품 페이지를 한 건도 보지 못한 채 100%를 선언한 것입니다.**

**해결**: 두 가지를 했습니다.
(a) **유효성 게이트** — 받아온 문서에 상품명 조각이나 가격이 없으면 판정하지 않고
`unreachable`로 둡니다. (b) **측정 가능한 것으로 옮겼습니다** — 상세는 37건 중 1건만
도달 가능하지만 상품명·스펙의 표기는 전수 측정할 수 있고, 그것이 논지에 더 맞습니다.
오리파는 "SAR 확정"처럼 **보장**을 광고하면서 **확률**은 적지 않습니다(확정 30건 vs 확률 0건).

> **배운 것**: 도달하지 못한 것을 측정값으로 세면 안 됩니다.
> 그리고 **너무 깨끗한 100%는 대개 아무것도 안 잰 것입니다.**

### ④ 고가 카드가 크롤러에서 조용히 사라졌습니다 (v1)

**문제**: 고가 카드 44건 중 40건이 없어졌는데 HTTP는 200이고 예외도 없었습니다.

**원인**: 다나와에는 자사 상품(`pcode=`) 외에 **중개 상품**(`go_link_goods.php?link_prod_c=`)이
섞여 있는데 `pcode`만 파싱하고 있었습니다. 고가 카드가 전부 중개 쪽이었습니다.

**해결**: 두 형식을 모두 받습니다. 그리고 **중개 상품이 1건 이상 수집됐는지를 self-check로**
만들었습니다 — 0건이면 파서가 한쪽만 보고 있다는 뜻이므로 실패로 판정합니다.
v2 크롤에서 중개 상품 820건이 수집됐습니다.

> **배운 것**: 크롤러의 진짜 실패는 예외가 아니라 **조용한 0건**입니다.

### ⑤ 차단어가 상품 본체를 지우고 있었습니다

**문제**: v1은 카드 차단 목록에 '슬리브'를 넣어 `"뮤 ex SAR 풀헤드 … 슬리브"`처럼
슬리브에 담겨 팔리는 고가 카드를 통째로 지웠습니다. 그건 고쳤지만 같은 종류가 남아
있었습니다 — `덱케이스`·`보관함`·`전용케이스`가 **액세서리 축에서는 상품 본체 이름**입니다.

**해결**: 차단을 축별로 나눴습니다. 그리고 통을 실제로 구성해 출력해 보니
A등급에 "유희왕 … 포켓몬카드"(키워드 스팸)가, C등급 최상단에 "홀로그램 종이 팝딱지"가
있었습니다. 포켓몬 TCG 판별기를 추가했습니다. 엄격하게 걸러도 4등급이 전부 성립합니다.

> **배운 것**: 차단어를 넣기 전에 **그 단어가 그 축의 상품 본체에 나타날 수 있는지**를 먼저 봅니다.

### ⑥ AI가 박스 구성을 무너뜨렸습니다 (v1) → v2에서 AI의 자리를 바꿨습니다

**문제**: v1은 ChatGPT가 박스 구성에 관여했고, 모델이 상품 id를 되묻기 보기(`options`)
필드에 넣는 사고로 박스가 무너졌습니다.

**원인**: 프롬프트로 형식을 지시하고 그 지시를 신뢰했습니다. **프롬프트는 부탁입니다.**

**해결**: v2에서 통은 서버가 확정한 뒤 고정되고, AI는 **선호 순위와 설명 문장만** 반환합니다.
그리고 가드를 코드에 뒀습니다 — 통 밖 id는 버리고(`keepValid`), 엉뚱한 필드에 흘린 id는
회수하고(`rescueIds`), 누락분은 서버가 시세 내림차순으로 채웁니다.
테스트가 "환각 id만 돌아와도 통이 온전한지"를 fetch 모킹으로 확인합니다.

> **배운 것**: 프롬프트는 부탁이고 **가드가 보증**입니다.

### ⑦ 교환이 거의 일어나지 않았습니다 — 그리고 그것이 제품에 대해 알려준 것

**문제**: 교환 전환율을 재니 남이 뽑은 S가 교환으로 나에게 오는 경우가 **1/174회(0.6%)**,
라운드당 교환 사이클이 **0.51개**였습니다. 절반의 방에서는 교환이 아예 없었습니다.
데모 화면에도 "성립한 교환이 없습니다"만 떴습니다.

**원인**: 버그를 찾다가 버그가 아님을 알았습니다. **제가 고른 규칙의 수학적 귀결이었습니다.**
선호의 2순위 이하를 "시세 내림차순"으로 채우면 **모두의 선호가 지목 카드 이후로
완전히 같아집니다.** TTC는 선호가 서로 엇갈릴 때만 사이클을 만듭니다.
전원이 같은 순서로 원하면 교환할 것이 수학적으로 없습니다.

**해결**: 검사를 완화하는 대신 두 극단을 나란히 재도록 바꿨습니다.

| 선호 모델 | S가 교환으로 내게 옴 | 전체 개선율 | 사이클/회 |
|---|---|---|---|
| 동질 — 전원 시세 내림차순 (AI 없음) | 1.9% | 10.5% | 0.51 |
| 이질 — 각자 다른 취향 (지목 + ChatGPT) | **51.9%** | **68.4%** | **2.54** |

**이 표가 지목과 ChatGPT가 장식이 아님을 증명합니다.** AI는 편의 기능이 아니라
메커니즘의 하중을 받는 부품입니다. 과제 요건을 형식으로 채운 것이 아니라는 근거가
코드 실행 출력으로 나온 셈입니다. 그리고 화면에 두 값을 나란히 띄웁니다 —
하나만 보여주면 제품을 실제보다 좋거나 나쁘게 말하게 됩니다.

> **배운 것**: 측정이 설계 결정을 반박하면, 검사가 아니라 설계를 고칩니다.
> 그리고 그 반박이 제품에서 무엇이 하중을 받는 부품인지 알려줍니다.

### ⑧ 배포했는데 화면이 안 바뀌었습니다 (v1) — 그리고 로컬에서도 같은 일이

**문제 (v1)**: 새 기능을 배포했는데 프로덕션이 여전히 옛 화면이었습니다.
도메인이 특정 배포에 고정돼 있었고(`vercel alias set`으로 수동 연결한 뒤의 `--prod`는
새 배포를 만들 뿐 도메인을 옮기지 않습니다), `/api/boxes`에 `s-maxage=3600`이 걸려
엣지가 한 시간짜리 응답을 들고 있었습니다.

**문제 (v2, 로컬)**: 같은 일이 로컬에서도 났습니다. 새 서버를 띄웠는데 응답에
v1에만 있던 `X-Pool-Crawled-At` 헤더가 있었습니다. `EADDRINUSE`로 새 서버가 죽고
옛 프로세스가 계속 응답하고 있었습니다.

**해결**: 캐시를 `s-maxage=60, stale-while-revalidate=600`으로 낮추고 테스트가 헤더
문자열을 직접 확인합니다. E2E는 매 요청에 `?v=랜덤`을 붙여 캐시를 우회하고,
**배포한 URL이 아니라 사용자가 여는 URL**에서 돌립니다.

> **배운 것**: "성공" 로그는 사용자가 새 화면을 본다는 뜻이 아닙니다.

### ⑨ 화면 숫자와 서버 숫자가 두 벌이 되려 했습니다

**문제**: 교환 전환율 표(51.9% 등), 오리파 실측(0/37건), "정확히 10.00배 / 9.87배" 문장이
JSX에 손으로 적혀 있었습니다. 엔진을 고쳐도 화면은 안 바뀝니다.

**해결**: 전부 코드 실행 출력에서 오게 했습니다.
`node api/_trade.js` → `data/conversion.json` → `/api/boxes` → 화면.
그리고 **화면 소스에 확률·배수 리터럴이 있으면 실패하는 검사**를 넣었습니다.
`toFixed` 호출이 있어도 실패합니다 — 화면이 계산하는 순간 두 벌이 됩니다.

### ⑩ 반올림이 100%를 만들고, 불가능한 상태가 100%로 표시됐습니다

**문제**: C등급 팀 10명 확률이 `100.000%`로 나왔습니다. 실제로는 1보다 작습니다.
그리고 갱신 확률표에서 B등급 j=990이 `100%`였는데, 990구좌가 빠졌으면 10구좌만
남는데 B 재고는 25장입니다 — **성립할 수 없는 상태**를 `Math.min(1, k/left)` 클램프가
확률 100%로 덮고 있었습니다.

**해결**: 9.85배를 10배라고 쓰지 않기로 해놓고 99.99999%를 100%라고 쓰고 있었습니다.
같은 종류의 거짓말입니다. `>99.999%` / `<0.001%`로 쓰고, 불가능한 상태는 `null`을 반환해
화면에 `—`로 둡니다. **확률 0이 아니라 불가능입니다.**

### ⑪ 모바일에서 본문이 화면 끝에 붙었습니다

**문제**: 390px에서 제목과 본문이 x=0에서 시작했습니다.

**원인**: `.wrap`이 좌우 패딩 16px를 주는데, 같은 요소에 함께 붙는 `.section`/`.hero`/`.foot`이
`padding: X 0` **단축**으로 그것을 0으로 덮고 있었습니다. 우선순위가 같고 파일에서
뒤에 있어 캐스케이드에서 이겼습니다.

**해결**: `padding-block`으로 바꿔 정의 순서와 무관하게 만들고, 회귀를 검사로 고정했습니다.
한글이 "통이 안 보입 / 니다"로 잘리던 것도 `word-break: keep-all`로 고쳤습니다.

### ⑫ 배포본에서 개봉이 404로 죽었습니다 — 로컬에서는 전부 통과했는데

**문제**: 로컬 테스트 103항목과 E2E 46단계가 전부 통과한 코드를 배포했더니,
평가자가 클릭하는 순서로 4단계째에서 `404 "방이 없다"`가 났습니다.

**원인**: **Vercel은 라우트마다 별개의 서버리스 함수를 띄웁니다.**
KV 환경변수가 없을 때 쓰는 메모리 폴백은 **함수 안에서만** 공유됩니다.
`/api/room`이 만든 방을 `/api/open`은 볼 수 없었습니다. 당시 별도 라우트였던
AI 기능이 저장한 선호 순위도 마찬가지로 교환에 도달하지 못하고 있었습니다.
(그 라우트는 이후 프로젝트 Q&A `api/ask.js`로 대체되면서 상태를 아예 갖지 않게 됐습니다.)
로컬 서버는 한 프로세스라 전부 같은 메모리를 봤고, 그래서 로컬에서는 안 보였습니다.

**해결**: 방을 바꾸는 동작을 `api/room.js` 한 함수로 모았습니다
(create/join/target/simPrefs/setPrefs/ready/open/trade/state).
상태를 갖던 보조 라우트는 방을 건드리지 않고 **계산해 돌려주기만** 하도록 바꿨고,
저장은 클라이언트가 `setPrefs`로 넘기되 **서버가 그 id를 통 안의 것으로 다시 검증**합니다.
부수효과가 없어져서 테스트하기도 쉬워졌습니다.

> **배운 것**: 로컬의 "한 프로세스"가 배포본의 "여러 함수"를 흉내내지 못합니다.
> 그리고 이번에도 **배포한 뒤 실제 URL에서 클릭해봐서** 발견했습니다.

### ⑬ 배포본 캐시 검사가 배포본에서만 실패했습니다

**문제**: `/api/boxes`의 `s-maxage=60`을 헤더 문자열로 검사했는데, 로컬에서는
통과하고 배포본에서는 `cache-control: public`만 와서 실패했습니다.

**원인**: **Vercel은 `s-maxage`와 `stale-while-revalidate`를 엣지에서 소비하고
클라이언트 응답에서 제거합니다.** 캐시는 정상 작동하는데 헤더로는 안 보입니다.

**해결**: 재려던 것은 "헤더에 그렇게 적혀 있는가"가 아니라 "실제로 캐시되는가"였습니다.
같은 URL을 두 번 요청해 `x-vercel-cache`가 `MISS → HIT`가 되는지로 바꿨습니다.

### ⑭ self-check가 조용히 실행되지 않았고, 자기 자신을 위반으로 판정했습니다

**문제 (a)**: 메인 모듈 판별을 `import.meta.url`과 `process.argv[1]`의 문자열 비교로 했는데,
경로에 한글이 있어 `import.meta.url`만 퍼센트 인코딩돼 절대 같아지지 않았습니다.
출력이 아예 없었습니다.

**문제 (b)**: "api/에 예산·곡선 파라미터가 없다"를 소스에 그 단어가 등장하는지로
검사했더니 **검사 자신의 정규식 리터럴이 걸려** `_draw.js`가 위반으로 나왔습니다.

**해결**: (a) `fileURLToPath` + `realpathSync` 비교. (b) 재려던 것은 "단어가 적혀 있는가"가
아니라 "그 이름으로 파라미터가 **선언**돼 있는가"였습니다. 선언 형태로 바꾸니 언급과
사용이 갈렸습니다.

## 5. 아쉬운 점 · 개선하고 싶은 부분

### 실제 / 시뮬 / 미구현

|---|---|
| 통 구성 · 확률 계산 · 비복원 추첨 | **실제.** 서버가 계산하고 시드로 재현 가능 |
| TTC 교환 | **실제.** 서버가 계산 |
| 크롤 데이터 875건 | **실제.** 다나와 2026-08-29 |

| 오리파 확률 실측 | **실제.** 단 상품 표기 기준이며 상세는 37건 중 1건만 도달 |
| 팀원 9명 | **시뮬.** 배지 표시 |
| 팀원의 취향(선호 순위) | **시뮬.** 시드 기반 셔플. 실제 사용자라면 지목 + ChatGPT가 채웁니다 |

| 멀티 디바이스 방 | **시뮬.** KV 연동 코드는 있고 환경변수(`KV_REST_API_URL`·`KV_REST_API_TOKEN`)만 붙이면 켜집니다. 지금은 서버리스 인스턴스 메모리를 쓰므로 여러 인스턴스로 스케일되면 방이 갈라집니다 |
| 결제 · 배송 | **미구현** |

### 한계

1. **H1을 검증하지 않았습니다.** 가설은 "교환 가능성이 확률형 구매의 진입장벽을 낮춘다"인데,
   MVP가 측정한 것은 대리 지표(교환 전환율·개선 인원 비율)뿐입니다. 실사용자 없이는
   진입장벽이 실제로 낮아지는지 알 수 없습니다.
2. **통 원가를 시세로 뒀습니다.** 다나와 최저가는 소매가입니다. 그래서 통 시가 합계가
   참여비 총액의 145.8%로 나옵니다 — 꽝 없음 1층의 구조적 귀결입니다.
   실제 매입가를 모델링하지 않았으므로 **이 숫자를 사업성 근거로 읽으면 안 됩니다.**
3. **전략 방지는 표본 검사입니다.** 정리로는 증명돼 있지만(Roth 1982) 우리 구현에 대해
   전수 확인한 것이 아닙니다.
4. **선호 이질성이 가정입니다.** 이질 모델은 무작위 순열입니다. 실제 수집 취향이 얼마나
   엇갈리는지는 측정하지 않았습니다. 근거는 E4(커뮤니티 교환이 실재한다)뿐입니다.
5. **오리파 상세 페이지에 도달하지 못했습니다.** 37건 중 36건이 중개 링크입니다.
   판매자 사이트를 직접 크롤하면 더 강한 근거가 되지만, 이번에는 하지 않았습니다.
6. **타깃 검증이 없습니다.** 30~40대 부모라는 것은 가정이고 인터뷰하지 않았습니다.
7. **자체 감사에 과제 안내문 전문을 쓰지 못했습니다.** 요건을 재구성해 감사했습니다.

### 확장 가능성으로만 남긴 것

데일리 100원 · 유니폼 공동구매 · 브랜드 협업 · 천장. 전부 v1에 구현돼 있었고
(`v1-final` 태그에 보존돼 있습니다) v2에서 의도적으로 뺐습니다.
올웨이즈에 이미 0원딜·다인딜이 있어 신규성이 없고, 천장은 비복원 추출이 대체하기 때문입니다.

### 검증하고 싶은 가설

1. 통을 보여주는 것이 실제로 구매 전환에 영향을 주는가 (A/B)
2. 교환 가능성이 첫 참여의 문턱을 낮추는가 (H1)
3. 실제 사용자의 선호가 얼마나 이질적인가 — 이 값이 교환의 가치를 결정합니다
4. "확률 대신 확정을 판다"는 관행이 오리파 시장 전체에서 어느 정도인가 (표본 확대)
